Chapter 13: Tracing And Tracebacks

Tracing is how XSH shows what happened at runtime without changing script stdout. It is useful when a process has the wrong argv, a scoped directory or environment change behaves unexpectedly, a stream stage fails, or a script is slower than expected.

By the end of this chapter, you should know how to start with a trace summary, when to switch to raw events, how to read process boundaries, and how propagated failures connect trace events to tracebacks.

Runtime Graphs

Source code is a tree: expressions contain expressions, blocks contain statements, and spans point back to fixed ranges in a file. Running code is a graph. A single source expression can start a process, connect argv, cwd, env, redirections, status, and captured output, then propagate an error through a different call path.

XSH keeps the source tree simple and makes the runtime graph observable through traces. Parent ids show dynamic containment. Source spans anchor events back to code. Event kinds and payloads describe process boundaries, structured stream stages, scoped cwd and env, parallel jobs, resource targets, and propagated failures.

That is why traces record argv as arrays, cwd and env as structured data, and errors as variants rather than reconstructed strings.

Start With A Traceable Script

This script calls a proc and then runs a process:

proc say(message: Str) {
  print $message
}

say("traced")
let done = run.text printf "%s\n" "done" ?
print done.trim()

That gives the trace two runtime shapes to record: a user proc call and an external command.

Tracing is invoked through xsht:

xsht trace examples/trace.xsh

Script stdout stays on stdout. Trace output goes to stderr unless a trace file is requested.

Read The Summary First

--trace by itself writes a concise summary. The text summary includes total event counts, script duration, function call timing, hot command and module operations, and source spans for slow calls when available.

For the script above, the generated preview looks like this:

│ metric          │   value │
├─────────────────┼─────────┤
│ events          │      12 │
├─────────────────┼─────────┤
│ timed events    │       0 │
├─────────────────┼─────────┤
│ script duration │       - │
└─────────────────┴─────────┘

function calls (duration µs)
┌────────┐

Use the summary first when the question is "where did time go?" or "which high-level operations ran?"

Switch To Raw Events When Shape Matters

Use --raw when you need the event stream:

xsht trace --raw examples/trace.xsh

Raw text trace output renders one event per line. Events include an id, parent id, depth, kind, optional source span, optional name, timing, and payload data.

The same example with normalized raw events looks like this:

id=1 parent=- depth=0 kind=script.enter name="script" span=examples/trace.xsh:1:1-3:2
id=2 parent=1 depth=1 kind=proc.enter name="say" span=examples/trace.xsh:5:1-5:14
id=3 parent=2 depth=2 kind=core.call name="print" api_id="core.print" span=examples/trace.xsh:2:3-3:1 argv=[b"traced"]
id=4 parent=3 depth=2 kind=core.result name="print" api_id="core.print" span=examples/trace.xsh:2:3-3:1
id=5 parent=2 depth=1 kind=proc.exit name="say" span=examples/trace.xsh:5:1-5:14
id=6 parent=1 depth=1 kind=run.start name="printf" api_id="run" span=examples/trace.xsh:6:12-6:41 target=b"printf" argv=[b"%s\n", b"done"] cwd=b"<cwd>"
id=7 parent=6 depth=1 kind=run.end api_id="run" span=examples/trace.xsh:6:12-6:41 status={kind:exit success:true code:0}
id=8 parent=1 depth=1 kind=method.call name="Str.trim" api_id="method.Str.trim" span=examples/trace.xsh:7:7-7:18
id=9 parent=8 depth=1 kind=method.result name="Str.trim" api_id="method.Str.trim" span=examples/trace.xsh:7:7-7:18
id=10 parent=1 depth=1 kind=core.call name="print" api_id="core.print" span=examples/trace.xsh:7:1-8:1 argv=[b"done"]
id=11 parent=10 depth=1 kind=core.result name="print" api_id="core.print" span=examples/trace.xsh:7:1-8:1
id=12 parent=1 depth=0 kind=script.exit name="script" span=examples/trace.xsh:1:1-3:2

Useful event kinds include:

  • script.enter and script.exit;
  • proc.enter, proc.exit, pure.enter, and pure.exit;
  • core.call and core.result;
  • module.call and module.result;
  • method.call and method.result;
  • run.start and run.end;
  • cwd.enter and cwd.exit;
  • stream.stage.enter and stream.stage.exit;
  • result.propagate and runtime.error.

For process work, inspect run.start: it records the executable target, argv array, cwd, and environment overlay. XSH records argv as structured items, not as a reconstructed shell string.

Write Traces For Tools

Use JSON when another tool should consume the trace:

xsht trace --trace-format jsonl examples/trace.xsh
xsht trace --raw --trace-format jsonl examples/trace.xsh

Without --raw, JSON trace format writes one summary object. With --raw, it writes one JSON object per trace event.

Use --trace-file to keep runtime stderr separate from trace output:

xsht trace --trace-file trace.txt examples/trace.xsh

On Linux, --syscalls runs the script under XSH's native ptrace supervisor and appends syscall totals:

xsht trace --syscalls --trace-top-syscalls 12 examples/trace.xsh

Other platforms reject --syscalls before the script runs.

Connect Failures To Tracebacks

Failures that propagate through ? carry trace events and traceback information:

proc fail() [process] {
  run false
}

fail()

The catalog expects this example to fail with status 3 and mention nonzero-exit.

A traceback includes the failing source span, user proc or pure function call stack, operation kind, structured error variant and message, and process details when the failure came from an external command.

How To Read A Trace

Start with the summary. If the summary points at the wrong operation, rerun with --raw and follow parent ids from the surrounding proc or stream stage down to the failing operation.

For process problems, inspect:

  • the run.start target and argv array;
  • the recorded cwd;
  • any environment overlay;
  • the matching run.end status or exec error.

For propagated failures, look for result.propagate, then read the traceback below the trace output. The trace shows runtime relationships; the traceback shows the user-facing failure path.

What You Know Now

Tracing turns XSH execution into structured evidence: summaries for the common case, raw event streams for debugging, JSON Lines for tooling, syscall summaries on Linux, and tracebacks for failures.
