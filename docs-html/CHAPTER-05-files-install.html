Chapter 5: Files And Install Workflows

Filesystem automation is where small scripts often become hard to audit. A script starts by listing files, then grows cleanup rules, install paths, permissions, tables, and checks that must be right on the first run.

By the end of this chapter, you will have seen the shape of a useful file report and a small staging workflow: paths stay typed, file records carry metadata, cleanup is scoped with defer, and text formatting happens at the last boundary.

Build A File Inventory

The first job is a project inventory. It walks the current tree, ignores hidden paths, groups files by extension, and prints stable counts.

# Implements fd -tf | awk -F. 'NF > 1 {print tolower($NF)}' | sort | uniq -c | sort -n with zero subprocesses.
let root = fs.cwd()?

let stats = fs.files(root, stat: false)
  |> where .ext != ""
  |> count { |entry|
    entry.ext.lower()
  }

let counts = stats.keys()
  |> map { |ext|
    {count: stats.get(ext, 0), ext: ext}
  }
  |> sort-by .count

for row in counts {
  print f"${row.count:>4} ${row.ext}"
}

This is a complete script, not just a stream demo. It asks the filesystem for records, filters those records while they are still structured, groups by a computed key, then formats each final row.

Why XSH shines here: fs.walk produces file records without spawning fd, awk, sort, or uniq; group-by keeps the extension attached to the matching entries; and the script only turns records into text when it prints.

Compared with bash and CLI tools: the shell version is usually a pipeline like fd | awk | sort | uniq -c | sort. That is fine for a quick terminal one-liner, but the intermediate format is text. In XSH, the script keeps paths, extensions, and counts as values until the final print.

Common trap: avoid turning paths into strings too early. Use path methods while you are deciding what the path means; use .display() when the path is ready to cross a text boundary.

Do not use XSH to replace every casual terminal pipeline. Use it when the file inventory becomes policy: filtering rules, install decisions, manifests, permissions, or checks that need review.

Filesystem capacity and mount ownership also stay typed. Use fs.filesystem_stats(path)?, fs.mounts()?, and fs.mount_for(path)? when a script needs disk usage or mount metadata; do not parse df output inside the script.

When a script combines a trusted root directory with untrusted relative names, use fs.open_root(root)? and the fs.root_* functions instead of joining path strings. Rooted filesystem operations resolve from an open directory handle and reject absolute paths, .., and symlink traversal.

Print A Table When Columns Matter

Counts are enough for a quick inventory. When a script needs columns that a person will scan, use table output as the final stage.

let root_handle = fs.tempdir()?
defer fs.close_root(root_handle)?
let root = fs.root_path(root_handle)?
fs.write(fp"${root}/small.txt", "a")?
fs.write(fp"${root}/large.txt", "abcd")?

fs.ls(root)
  |> sort-by .size
  |> table.print(columns: ["name", "size", "kind"])

let process_count = process.list()
  |> where .pid > 0
  |> count()

let has_processes = process_count > 0
print $has_processes

The script creates a temporary directory, writes two files, sorts file records by size, and prints named columns. The process-count check is deliberately separate: it shows that host state also arrives as records and can be checked without parsing command output.

Why XSH shines here: a table is presentation, not the internal data model. Earlier pipeline stages still work with records, numbers, and paths.

Do not parse table output later in the same script. If another step needs the data, keep the records and print the table only for the human reader.

Stage A Build-Like Output

Install and build recipes usually need a scratch root, source files, command boundaries, artifacts, and final verification.

let root = fs.tempdir()?

fs.root_write(
  root,
  p"main.c",
  """int main(void) { return 0; }
""",
)?

run printf "%s\n" "build ok"

fs.root_write(
  root,
  p"main.o",
  """object
""",
)?

let exists = fs.root_exists(root, p"main.o")?
print $exists
fs.close_root(root)?

The example simulates a build without depending on a compiler. The important shape is the workflow: create a temp root, write inputs, run an external boundary explicitly, write the artifact, and assert that the expected path exists.

Why XSH shines here: the script reads like a build recipe while retaining typed paths, scoped cleanup, and visible process execution.

Compared with bash and CLI tools: mktemp -d, trap, mkdir -p, cp, and chmod can express the same workflow, but correctness depends on quoting, cleanup discipline, and exit-status checks at every step. XSH makes temp roots, paths, cleanup, and failures first-class parts of the script.

Anchor Project-Aware Scripts

Project-aware tools should not depend on the directory where the user happened to run them. fs.gitroot() walks up from the current working directory to find the nearest .git directory and returns it as a Path.

let root = fs.gitroot()?
let cfg = fs.read_text(fp"${root}/tool.toml")?

It also works as a guard:

let _ = fs.gitroot()?

Outside a git repository, ? propagates a clear not-a-git-repo error before any downstream operation can fail cryptically.

Source: examples/idiom-gitroot.xsh.

What You Know Now

File scripts are easier to trust when they keep three boundaries separate: filesystem paths, structured metadata, and final user-facing text. The next chapter uses the same habit for text, bytes, and hashes.
