# Pure-XSH btop: unattended implementation campaign

## 1. Agent mandate

Implement a useful, increasingly btop-compatible system monitor whose application, collection/parsing policy, derived metrics, state management, layout, widgets, graphs, configuration, and interactions are written in XSH. Use this application to improve XSH's reusable TUI capabilities and expose genuine language/runtime deficiencies.

**Deliver the first small, real, deterministic TUI before attempting the whole application. Then continue automatically through the remaining gates. Gate 1 is a checkpoint, not the end of the assignment.**

Work in the existing XSH repository. Do not create a separate monitor written in Rust, a wrapper around upstream btop, or an alternative XSH interpreter. Do not merely produce a design or scaffold. Implement, test, measure, fix, document, and commit coherent increments. Use the current repository's `AGENTS.md` and testing contracts, not commands remembered from older versions of XSH.

The primary completion target is **btop v1.4.7 feature parity on Linux**, qualified by actual hardware capabilities. Linux is the first live collector because the existing system-report contract is Linux-specific. Keep the pure model, reducer, and renderer portable. A final section defines the separate macOS/BSD parity track; do not confuse cross-platform replay tests with live OS support, or let a missing BSD runner prevent completion of the Linux product.

Operate unattended. Resolve ordinary design details from this document and nearby code. Do not ask the user to choose names, approve each stage, supply synthetic fixtures, or manually inspect routine goldens. For an actual external blocker—missing runner, device, credential, or permitted capability—record exactly what is blocked, continue all independent work, and never label an unexercised lane as passed.

### 1.1 Non-negotiable boundaries

1. **XSH owns domain behavior.** Native code may expose reusable OS, descriptor, terminal, numerical, Unicode, and byte operations. A native performance exception requires an XSH implementation and measurements identifying the smallest operation needing acceleration. This follows the repository's existing architecture contract, rather than inventing a different purity standard for this project. [X2]
2. **Production starts no helper process.** Do not shell out to `btop`, `top`, `ps`, `df`, `free`, `ip`, `sensors`, `nvidia-smi`, `stty`, `tput`, Python, or another XSH process. Reference utilities, fixture generators, terminal emulators, profilers, and owned test children belong in the development harness only.
3. **Use canonical rooted collectors.** Direct procfs/sysfs acquisition belongs in `core/lib/sys_*.xsh`, through the shared rooted source boundary. Do not put `/proc` and `/sys` parsing in `core/btop.xsh`, duplicate system-report parsers, or use native live-only `linux.sample()` as the final monitor implementation. [X4, X8, X11]
4. **One implementation serves live and replay.** Replay replaces observations, clocks, terminal events, and effects; it must not substitute a second set of parsers, rate calculations, or widgets.
5. **Existing contracts survive.** Preserve system-report JSON v1, its redaction policy, its no-command-line/no-environment process policy, and existing applet behavior. Preserve the current scalar-counting `tui.left_pad` and `tui.right_pad` contract unless a deliberate, separately justified migration is required. Add display-cell APIs instead. [X4, X9, X10]
6. **Do not move the goalposts.** Freeze stage requirements and upstream feature inventory before implementation. A missing capability is not zero; untested is not passed; a fixture generated by the candidate is not an independent expected result.

These constraints do not prohibit useful XSH expansion. They prohibit evading the exercise by hiding the application behind a native intrinsic.

## 2. Research findings that should change the implementation

### 2.1 System-report is the foundation, not an external command to invoke

The inspected tree already has a typed, bounded, subprocess-free report with a strong separation between source collection, report construction, serialization, presentation, and development-time reference checking. Its `sys_pci`, `sys_usb`, `sys_block`, and `sys_mount` modules are shared kernel-ABI models; `system-report` is one consumer, not their owner. The same caller-owned `FsRoot` serves a live source tree, synthetic fixtures, and captured trees. [X4–X8]

Start with these owners:

| Existing owner | Reuse here | Do not do |
|---|---|---|
| `core/system-report.xsh` | CLI/error/replay conventions, bounded input handling, typed entrypoint pattern | Invoke it once per frame or parse its text output |
| `core/lib/system_report.xsh` | Observation vocabulary, source scope, types, CPU-list semantics, wire-boundary conventions | Inflate every dynamic sample into the entire report; silently change JSON v1 |
| `core/lib/system_report_collect.xsh` | Existing parsers and transitional wrappers; identify extraction points | Add another independent parser for the same ABI |
| `core/lib/system_report_live.xsh` | Static discovery, identity/race handling, mappings from shared collectors | Run full firmware/topology/device discovery every refresh |
| `core/lib/sys_source.xsh` | Bounded reads, complete-observation rule, field-addressed issues, numeric lexical checks | Turn incomplete reads into valid-looking prefix values |
| `core/lib/sys_block.xsh` | Device identity, stacking, raw I/O fields | Reparse `lsblk`/`iostat` output or confuse a gauge with a counter |
| `core/lib/sys_mount.xsh` | Mount IDs, mount relationships and source observations | Query the replay machine's mount capacity and call it fixture data |
| `core/lib/sys_pci.xsh`, `sys_usb.xsh` | Hardware identity and relationship joins | Re-enumerate everything just to label one sensor |
| `dev/system_report_check.xsh` | Raw capture/replay and independent-reference patterns | Append the entire new campaign to this already substantial file |
| `dev/system-report-coverage.json` | Fixed-denominator assertion model | Let candidate output determine which assertions are eligible |

Extract missing shared CPU, memory, process, network, sensor, and power readers into appropriately named `sys_*` modules as needed. Existing wrappers can delegate during the migration. Re-run the report's tests whenever a shared reader changes. New names are proposals, not assertions that all these modules already exist.

### 2.2 Inventory and telemetry are different workloads

System-report primarily answers “what is present, what was observed, and under which scope?” A monitor must additionally answer “what changed over this measured interval?” Use static or slowly changing inventory plus lightweight repeated samples. Do not make a full report the inner-loop data structure.

Keep topology, device relationships, boot/scope identity, labels, mount enumeration, and capabilities separately from cumulative counters, current gauges, and derived rates. Refresh each according to its cost and invalidation needs. A process table should not require rereading firmware, PCI identity, CPU vulnerabilities, every mount's capacity, or every process's command line on every tick.

### 2.3 The existing `top` is useful evidence, not the final architecture

`core/top.xsh` is batch-only and calls native `linux.sample()`. Its previous-process lookup filters the full previous process list for every current process, matching PID and start ticks. That is an O(P²) historical join. Replace this pattern with an identity-keyed index in the new monitor; later share the improvement with `top` if its contract can be preserved. [X11]

`core/lib/procps.xsh` already provides CPU percentage logic and explicitly avoids double-counting guest ticks. It also handles a downward iowait correction. Reuse or carefully factor that mathematics rather than starting from a blog post. However, its batch-oriented “since boot on first sample” and error-on-counter-reset behavior should not be imposed blindly on an interactive monitor. The latter needs warming/reset/unavailable states without terminating the whole UI. [X12]

### 2.4 TUI needs a substantial expansion, not more escape-string constants

`stdlib/tui.xsh` currently supplies ANSI sequence helpers. `src/modules/tui.rs` contains padding and secret input. Existing padding counts Unicode scalar values after a limited escape scan; `tests/xsh/stdlib/tui.xsh::test_tui_pad_counts_unicode_scalars` explicitly specifies that behavior. This is not an accidental behavior to “fix” by silently changing its tests. [X9, X10]

The application needs an owned terminal session, timed input, incremental event decoding, deterministic geometry, display-cell-aware clipping, structured styling, compositing, damage tracking, buffered output, and cleanup under failure. The current `core/more.xsh` demonstrates `unix.window_size(1)` and terminal-related host tests, but its interactive input is line-oriented and requires Return. It is not a substitute for raw key handling. [X13]

### 2.5 Pin the upstream target and separate kinds of parity

The researched latest release is btop v1.4.7, released 1 May 2026. Pin its commit, not moving `main`. Its source separates shared data and drawing, Linux collection, input handling, menus, configuration, and themes. Use those boundaries to inventory behavior; do not transliterate its global state and threading structure into XSH. [B1–B7]

Maintain independent columns for **data correctness**, **interaction compatibility**, **visual compatibility**, **performance**, **platform coverage**, and **hardware coverage**. These are not interchangeable. An attractive four-panel screenshot does not prove correct CPU rates; a parsed `/proc/stat` fixture does not prove safe raw-mode cleanup.

Upstream's license is Apache-2.0 at the pinned release. Preserve applicable notices for any translated or copied source/assets and check individual third-party components. Do not assume every vendored GPU component or theme has identical provenance. Keep this a provenance task, not a reason to stop implementation. [B8]

### 3.1 Data flow

```text
live FsRoot / replay source observations + recorded scalar OS observations
                    |
             canonical sys_* readers
                    |
       raw typed inventory and cumulative samples
                    |
           exact interval derivation
                    |
  typed events ---> pure reducer ---> explicit requested effects
                    |
       deterministic view/layout model
                    |
      reusable XSH TUI widgets and surface
                    |
       XSH damage/encoding implementation
                    |
          owned native terminal session
```

Keep pure functions independent of the filesystem, clock, environment, terminal, and process operations. Suggested semantic boundaries—not existing API signatures—are:

```text
initialize(config, capabilities, inventory) -> State
parse_sources(raw_observations, source_units) -> RawSample
derive(previous_raw, current_raw, interval_context) -> DerivedSample
reduce(state, event) -> { state, requested_effects }
layout(viewport, enabled_panels, config) -> Layout
render(state, layout, display_policy) -> Surface
present_delta(previous_surface, next_surface) -> EncodedFrame
```

Pure does not require gratuitously copying all state every frame. Use the language's existing efficient ownership/update patterns; improve generic runtime operations if measurements expose pathological copying.

### 3.2 State and identity

Use typed records/unions, not a bag of dynamic `Record` values in the hot path. Keep wire decoding at a narrow boundary. At minimum distinguish:

- source scope and boot/session identity;
- stable inventory versus latest observations;
- raw counters versus derived rates;
- data availability versus temporal validity;
- selected process identity versus its current row number;
- history storage versus viewport width;
- collection scheduling versus UI state;
- requested effects versus effect results.

A process key includes the source session/namespace, PID, and start ticks. PID alone is insufficient. CPU histories use actual sparse logical IDs. Device histories use stable identities within their observed scope plus an epoch for removal/replacement. Network interface names alone must not carry history across replacement. Never assume the set of processes or devices stays fixed between list and read operations.

Keep `warming`, `reset`, `stale`, and `gap` in the monitor's temporal model; do not add undocumented values to system-report's stable JSON-v1 observation enums.

## 6. Gate 1: the deliberately small, real monitor

### 6.1 Required behavior

Create `core/btop.xsh` with a four-panel, monochrome/ASCII presentation recognizable as the CPU, memory, network, and process arrangement of a basic btop view. At this gate, **matching means the selected basic information, panel structure, updating behavior, and minimum interactions—not pixel-identical reproduction of upstream's default decorated screen**. Capture the chosen upstream basic configuration as a reference so this scope is explicit.

The first screen must show:

| Panel | Minimum content |
|---|---|
| CPU | Aggregate interval CPU usage with a simple meter; uptime and load when observed |
| Memory | Total, available, used under the documented convention; swap total/used or observed absence |
| Network | One deterministically selected interface, RX/TX interval rates and cumulative totals |
| Processes | PID, numeric UID when observed, command name, interval CPU, RSS; descending CPU order with stable tie-breaks |

Support `80×24` and `120×40`; below the chosen minimum, render a safe small-terminal message without crashing or reading out of bounds. Use fixed layout rules for this gate. Empty, unavailable, and zero values must remain visibly distinguishable. The first rate sample is warming/unknown, not fabricated inactivity.

Provide immediate `q` and Ctrl-C exit, without requiring Return; a periodic refresh; resize handling; and terminal restoration. No process actions. A whole-frame buffered redraw is acceptable here. Per-character writes, shelling out to set terminal modes, and calling a full report per tick are not.

Do **not** implement GPU, themes, settings menus, mouse, configurable layouts, process tree, expensive details, smaps, signals, or renice in this gate. A minimal in-memory surface and meter are enough; sophisticated graph work belongs later.

### 6.2 Proposed CLI contract

These are new interfaces to implement and document, not existing XSH commands:

```text
xsh core/btop.xsh --                         Live terminal monitor
xsh core/btop.xsh -- --replay BUNDLE          Interactive deterministic replay
xsh core/btop.xsh -- --replay BUNDLE --headless
xsh core/btop.xsh -- --replay BUNDLE --headless --dump-model MODEL.jsonl
xsh core/btop.xsh -- --replay BUNDLE --headless --dump-screen SCREENS.jsonl
xsh core/btop.xsh -- --frames N              Bounded diagnostic/test execution
```

Verify the existing launcher's argument separator locally and use its canonical spelling in the final docs. Define whether `--frames` counts presented frames, completed samples, or both; use distinct options if tests require both. A replay must terminate at the end of its finite event stream without sleeping in real time. Its action backend must never target live PIDs.

Do not claim to accept the whole btop CLI yet. Reject unsupported options clearly rather than silently ignoring them. Add CLI compatibility as a mapped Gate-4 surface.

### 6.3 Required acquisition path

Use the shared rooted source boundary for raw CPU, memory, uptime/load, selected interface counters, and process identity/statistics. Extract the smallest shared parsers needed from existing report code, preserving wrappers and report tests. Add canonical `sys_*` pieces when absent. Avoid `linux.sample()` as a hidden implementation shortcut.

Inject page size, clock ticks per second, monotonic observation times, and source identity. A source root by itself does not encode these values. Use the same acquisition/parsing functions for live and raw replay.

### 6.4 First deterministic numerical fixture

Use synthetic, deliberately simple numbers. For a two-logical-CPU source with 100 ticks/second, a 4096-byte page, and exactly one second between observations:

```text
                      t0                         t1
/proc/stat aggregate  user=100 system=50          user=160 system=70
                      idle=850, other=0          idle=970, other=0

PID 42, same start    process cpu_ticks=10        process cpu_ticks=35
                      RSS=16384 pages             RSS=16384 pages

interface RX bytes    1,000,000                   1,010,240
interface TX bytes      500,000                     502,048

MemTotal              1,048,576 kB                unchanged
MemAvailable            262,144 kB                unchanged
```

Independently expected results at t1:

```text
aggregate CPU:        (60 + 20) / (60 + 20 + 120) = 40.0%
PID 42 one-core CPU:  25 / 100 / 1 × 100 = 25.0%
PID 42 total-machine: 25.0 / 2 = 12.5%
PID 42 RSS:           16384 × 4096 = 67,108,864 bytes = 64 MiB
RX rate:              10,240 bytes/s = 10 KiB/s
TX rate:               2,048 bytes/s = 2 KiB/s
used memory:          1 GiB - 256 MiB = 768 MiB
```

Choose and label the default process CPU convention. The pinned btop configuration defaults to total-machine normalization (`proc_per_core=false`); use 12.5% for that baseline and separately test the 25% mode. Do not compare values computed under different denominators. [B3]

The fixture files must have complete, valid kernel formats, including the full required process-stat fields—not pseudo-files containing only the lines above. Write a small independent synthetic-fixture builder if useful. Assert the raw file bytes/digests and expected arithmetic. The values above are the oracle, not outputs to regenerate from candidate code.

Add first-gate cases for cold start, a subsequent idle interval, empty process enumeration, process disappearance/reuse, an unavailable interface, malformed/truncated memory input, and a resize followed by exit. More extensive adversarial cases come later, but the thin slice must already retain source states.

### 6.5 Gate-1 exit conditions

- The live monitor works in the pinned Linux environment without external helpers.
- Raw two-sample replay produces the expected typed metrics and deterministic screen cells.
- Replaying the same bundle repeatedly is independent of host time, environment, PID set, and terminal size when those inputs are supplied by the bundle.
- A PTY test drives the **actual entrypoint**, observes two updates, injects resize and `q`, and verifies exit and restored terminal attributes/modes.
- A noninteractive replay runs without a TTY and without sleeps.
- A source-access/subprocess check finds no child exec and no out-of-scope live acquisition in replay.
- Shared collector and existing system-report tests remain green.
- The gate has a committed evidence summary and usable invocation instructions, not only screenshots.

After this passes, commit the vertical slice and proceed automatically to Gate 2.

## 7. Gate 2: make `tui` a serious reusable XSH module

Do not replace the minimal Gate-1 implementation wholesale. Grow it in independently tested increments. Keep terminal mechanics separate from pure rendering and application policy.

### 7.1 Owned terminal session

Introduce or extend a generic managed terminal resource using the existing XSH resource model. Reuse existing host dependencies such as `rustix` where adequate; do not add a native UI framework or an async runtime by default. The exact public spelling must follow the registry audit. The required capabilities are:

| Capability | Contract |
|---|---|
| Open/enter | Validate descriptors and interactivity; capture original attributes; enter requested modes transactionally |
| Size | Return rows/columns from the owned terminal; replay receives explicit values |
| Timed receive | Wait for input, resize/cancellation, or deadline without busy-spinning |
| Output | Send a bounded buffered frame; surface short writes, errors, and backpressure |
| Suspend/resume | Restore before suspension; reacquire modes and redraw after continuation |
| Close | Restore changed modes and attributes; tolerate partial initialization and repeated cleanup |

Define what happens when stdin is a pipe, stdout is redirected, no controlling terminal exists, an inherited descriptor is closed, or the terminal disappears. Do not accidentally consume piped application data as keyboard input. A headless replay does not open a terminal. An explicitly interactive invocation without a usable terminal should fail with a useful error before changing anything.

In the first version, one active session owns a given terminal. Do not add a global session daemon, terminal broker, background manager, or general application server. Reuse runtime cancellation and signal machinery. Do not run XSH code, allocation-heavy logic, or terminal restoration directly inside an asynchronous POSIX signal handler; hand off through the established safe mechanism.

Choose raw/cbreak flags deliberately. If the chosen mode converts Ctrl-C into a byte, the input layer must turn it into cancellation; if it leaves signal generation enabled, the runtime must perform managed cleanup. Test both explicit signal delivery and actual Ctrl-C input. Apply the same deliberate policy to Ctrl-Z.

Exercise normal return, `q`, Ctrl-C, SIGINT, SIGTERM, EOF/hangup, write failure, an XSH runtime error during rendering, and partial session initialization. Later exercise suspend/continue. Assert original termios attributes, cursor visibility, alternate-screen exit, mouse/paste modes, and style reset to the extent each was changed. No implementation can promise restoration after SIGKILL or a terminal transport that can no longer accept output; document that boundary rather than claiming impossible guarantees.

### 7.2 Monotonic deadlines and responsiveness

Audit existing public time and polling APIs first. Add the smallest reusable monotonic-clock and descriptor/event-wait primitives only if needed. Use the established effects and error vocabulary. Do not add a btop timer intrinsic or a second scheduler just for this program.

Use deadlines, not `collect; render; sleep(interval)`, which adds work time to every refresh. Initially one event loop is preferable. Keep collection steps bounded and cooperative; render or process input between bounded batches where needed. Decouple “sample due” from “sample completed.” Coalesce overdue sampling work rather than queuing an unbounded backlog.

If measurements prove blocking acquisition prevents the input budget, use existing bounded concurrency or extend a genuinely reusable facility. A worker may return typed samples, never write to the terminal. One component owns presentation. Limit concurrent work, input queue length, and retained samples; record dropped/coalesced sample events so replay semantics remain explicit.

Use monotonic time for intervals. Wall-clock jumps may change the decorative clock but must not create negative rates or a flood of catch-up ticks. Define suspend behavior: on a detected discontinuity, reset or mark interval baselines rather than silently blending a long pause into ordinary live data.

### 7.3 Incremental event decoding

Implement the protocol-decoding policy in XSH unless a measured, reusable byte-decoding primitive is needed. Feed it chunks, not an assumption that one read equals one key.

The initial decoder must handle ASCII controls, UTF-8 text, CSI/SS3 arrows and navigation keys, function-key forms used by the selected compatibility keymap, EOF, and an incomplete sequence. Give a lone Escape a bounded timeout so it is distinguishable from an escape-prefixed key. Make that timeout and virtual-clock progression replayable.

Add SGR mouse events, modifiers, wheel events, and bracketed paste as the UI begins using them. Ignore or reject unknown sequences under a bounded rule; never accumulate an unlimited unterminated escape or paste. Treat pasted text as text: a paste containing `q`, Enter, or a signal hotkey must not accidentally activate an action. Reject a control sequence's claimed enormous parameters without allocating enormous buffers.

Test every split point in each supported byte sequence, multiple keys in one read, interleaved resize/input, malformed UTF-8, Escape timeouts, oversized paste, unsolicited terminal responses, and unknown CSI sequences. Use xterm's control-sequence documentation for the supported encoding definitions, not an assortment of ad hoc regexes. [T1]

### 7.4 Cell-aware text and structured styles

Add new cell-aware operations rather than changing legacy scalar padding implicitly. Proposed capabilities include display width, clipping to cells, cell padding, and safe single-line text. The exact API names remain subject to existing naming conventions.

A rendering surface should know its dimensions, grapheme/glyph content, effective style, and the continuation cells occupied by a wide glyph. Storage can be packed arrays or row runs; the semantic model does not require allocating a heap record for every cell.

Pin a display policy: Unicode data/version, ambiguous-width convention, handling of unsupported/zero-width clusters, and ASCII fallback. Unicode East Asian Width by itself is not a complete terminal-width algorithm; use a tailored, tested policy. [T2] Test combining marks, CJK, emoji sequences, leading combining marks, malformed source bytes, tabs, and clipping at a two-cell glyph boundary. Do not promise identical display width across every font and terminal implementation.

Separate `Text`/glyph data from trusted styling operations. A process name containing ESC, OSC, carriage return, a bidi control, or a line separator must not move the cursor, set the window title, alter the clipboard, spoof another row, or leave an unclosed style. Reuse system-report's relevant sanitization policy without applying its full report redaction to the local interactive view.

Do not take arbitrary raw ANSI embedded in data and call it a styled label. Preserve the source value separately from the sanitized display value; replay/export privacy rules apply independently.

### 7.5 Surfaces, clipping, and delta presentation

Develop pure rectangle intersection, clipping, borders, labels, meters, table rows, selection highlighting, viewport scrolling, and the small input field needed for process filtering. Define empty/negative geometry behavior at validated boundaries and cap extreme viewport allocations.

Retain a previous **committed** surface and compare it with the next one. Emit a small number of cursor/style/text runs. Correctly clear shortened rows, erased overlays, trailing text, resized regions, and both halves of a replaced wide glyph. Test the terminal's rightmost column and bottom-right cell; do not accidentally scroll the display through autowrap.

Only advance the committed surface after the full frame has been written successfully. If a write is partial or a frame is abandoned, invalidate the assumed terminal state and recover with a controlled redraw. Never drop an encoded delta and then diff the following frame against a screen the user never received. Coalescing must operate on desired state, not an invalid chain of patches.

Synchronized-update escape sequences may be a later capability, but they do not replace a correct frame model. Always close such a transaction on handled failure. Baseline operation must remain correct when the terminal does not support synchronized output.

An unchanged frame should produce no content updates, apart from explicitly enabled liveness behavior. A forced full redraw must reproduce the same semantic screen as applying the sequence of deltas. Keep whole-frame clearing out of the ordinary steady-state path after this gate.

### 7.6 Interaction delivered by Gate 2

Add process selection, scrolling, sort choice and reverse order, filter editing and clear/cancel, and stable selection through ordinary process reordering. Selection follows process identity, not the row occupying a previous screen position. At this stage the UI remains read-only.

Provide a minimal generic test application exercising a scrolling table, an input field, resize, and an overlay using the same public TUI functions. Keep it in the nearest native-test corpus unless it qualifies as a substantial example under `AGENTS.md`. This proves the result is a reusable TUI module rather than a btop-shaped native interface.

### Gate-2 exit conditions

All Gate-1 fixtures still pass. Public TUI contracts have native tests and registry docs. PTY tests prove cleanup and byte-to-event behavior. Pure surface tests prove clipping and width semantics. An independent terminal decoder agrees with the surface after full and delta rendering. A deterministic interactive replay covers filter/edit/selection/resize. Input latency is measured independently of the collection interval. No monitor-specific native renderer, widget, or state machine was introduced.

## 8. Gate 3: correct, efficient Linux telemetry

The objective here is trustworthy data and stateful behavior, not complete theme or menu compatibility. Add data families in small vertical increments: raw fixture → canonical reader → interval derivation → visible field → reference check → performance measurement.

### 8.1 Shared extraction and scheduling

Create a reader inventory showing each monitor field, its kernel/OS source, owning `sys_*` function, unit, counter/gauge classification, static/dynamic classification, bounds, and relevant existing report tests. Any newly extracted parser must leave existing callers working.

Use at least these scheduling classes, with exact intervals/configuration recorded in the run:

| Class | Typical members | Policy |
|---|---|---|
| Startup/invalidated inventory | CPU topology, boot/scope, device identity | Initial discovery; refresh on observed changes and bounded periodic validation |
| Frequent counters | CPU accounting, network counters, process CPU/RSS | Main sample deadline |
| Less frequent gauges | Temperatures, frequencies, battery readings | Separate configurable deadline; do not starve main sampling |
| Slow/possibly blocking | Mount capacity, expensive details/vendor operations | Opt-in/on-demand or bounded isolated acquisition; cache with age/status |
| Selection-dependent | smaps, detailed process I/O, full arguments | Only the selected/requested entity; identity checked again |

Cache invalidation is part of correctness. Do not cache command/UID metadata forever merely because PID/start ticks are unchanged: an exec or credential change can alter those fields. Use safe refresh triggers or TTLs and explicitly stale values. Evict exited identities and old device epochs so churn does not cause unbounded memory growth.

### 8.2 Exact rate and validity rules

Document these rules in the monitor contract and test them as pure functions:

**Interval timing.** Use actual monotonic observation times, ideally per source/subsystem when acquisition spans are material. Record start/end or midpoint plus acquisition bounds. Never divide by the requested sleep duration merely because it is convenient. A zero/nonpositive interval yields an invalid temporal state, not division by zero.

**First observation.** A cumulative counter without a compatible predecessor has no interval rate. Display warming/unknown, or an explicitly labeled since-boot metric if that mode is requested. Do not imply it was measured over the last refresh.

**Reset and wrap.** Counter decrease is a reset/invalid interval unless the source has a known modular width and a tested wrap policy. A changed boot/session/device/process identity resets its baseline. Never clamp every negative difference to zero and call it observed inactivity. Handle iowait corrections under the documented CPU-specific policy, separately from a general counter reset. [X12]

**CPU accounting.** Avoid double-counting guest time already included in user/nice. Keep aggregate, per-core, idle/iowait treatment, and upstream rounding conventions explicit. Sparse IDs and CPU hotplug are fixtures. Do not silently change the existing `procps.cpu_percent` API's legacy behavior to satisfy a monitor-only convention.

**Process CPU.** Test both one-core normalization, which may exceed 100% for a multithreaded process, and total-machine normalization. Name the actual denominator. Host logical-CPU capacity, CPU affinity, and a cgroup quota are not interchangeable. Match the selected upstream convention for compatibility tests; any cgroup-aware alternative is an explicit mode, not a hidden denominator change.

**Memory.** Preserve raw observed counters and the selected derivation convention. `MemTotal - MemAvailable` is the basic used-memory convention here. An absent `MemAvailable` is not an observed zero; a fallback estimate must be separately specified and tested. Do not sum overlapping memory categories to force a total. Preserve swap absence and zero usage as different facts where the source distinguishes them.

**Block I/O.** Reuse the existing complete 11/15/17-field parsing and forward-field policy. Distinguish cumulative fields from `in_flight`, which is a gauge. Linux accounting sector values use 512-byte sectors; do not substitute the device's reported physical sector size. Preserve device layers rather than naively adding a disk and its partitions or stacked devices into a double-counted total. [X4, K2]

**Mount usage.** Distinguish available-to-user space from free space and the corresponding percentage convention. Rooted replay must use captured capacity results, not `statvfs` of a similarly named live mount. The existing report already separates mount inventory and local usage. [X4]

**Network.** Compute byte rates over the measured interval; keep binary/decimal and byte/bit display conventions explicit. Preserve interface identity through rename where justified; reset after replacement. Do not apply traffic deltas across unrelated network namespaces.

**Sensors and power.** Preserve signed values where the ABI permits them, stable channel identity, units, and absent/failed observations. Do not convert battery charge to energy without the necessary observed information, or advertise a requested CPU frequency as measured clock speed. [X4]

**Wide counters.** Do not force long-running kernel counters through floating-point JSON numbers. Keep system-report v1's existing exact-JSON bound intact. Use an explicitly versioned monitor wire representation with canonical decimal strings for wide counters and exact internal arithmetic. Audit XSH's available integer range and unsigned operations. If that surface is insufficient, add the smallest general exact-counter capability or a tested XSH representation; do not introduce a btop-specific integer intrinsic or a gratuitous general BigInt subsystem.

### 8.3 CPU, memory, storage, network

Add per-core history, logical CPU summaries, load averages, observed frequency modes, observed package/core temperatures, and uptime. Use canonical topology/labels as metadata, not as a prerequisite for CPU utilization when topology is unavailable.

Add memory/swap histories and the declared memory categories; device capacity and read/write I/O rates; interface selection, aggregate counters, and network histories. Keep inaccessible mounts/devices as partial data without losing valid neighbors. Test no swap, zero-sized mounts, sparse hardware, disappearing interfaces, mount escapes, loop/stacked devices, and optional fields.

Advanced views such as PSI and cgroup context may be useful XSH extensions, but do not let them displace required btop behavior. Put them in a separate extension column of the feature matrix.

### 8.4 Process table, tree, and detail

Use an indexed previous-sample map, not the existing `top` nested scan. Build parent/child adjacency once per sample. Detect self-parenting, cycles, missing parents, PID reuse, and disappearing rows without recursive native-stack failure. Tree aggregation must not double-count a child, and sorting/collapse must have deterministic tie-breaks.

Implement the pinned release's sorting modes, tree presentation and aggregation, filtering, selection, following, collapse/expand, and detail data as successive increments. Distinguish visible rows from the complete retained process set; rendering only visible rows is good, but omitting data required for correct sorting/aggregation is not.

**Preserve report privacy.** The existing system-report never reads process environments or command lines, even in sensitive mode. Keep that true. The monitor may add a separate full-arguments feature with explicit enablement and bounded reads, in a monitor-specific view over a shared raw reader. It must never read environments. Capturing/exporting full arguments requires separate opt-in because local interactive display and shareable capture have different disclosure risks. [X4]

Bracket identity around multi-file process acquisition. A name containing parentheses or whitespace must not break `/proc/[pid]/stat` parsing. Do not rely on naive whitespace splitting of the command field. Preserve unknown values on permission failures. Treat selected-process `smaps` and other expensive detail reads as on-demand; stale/error values must remain labeled.

### Gate-3 exit conditions

Every required Linux data family has raw synthetic fixtures, pure derived-value assertions, screen assertions, and independent reference evidence where applicable. Process/CPU/device churn leaves no history contamination or unbounded cache. Report regressions pass. The reader inventory demonstrates shared ownership instead of duplicate parsers. Scaling tests show indexed process matching rather than quadratic behavior. The monitor remains usable when optional sources disappear.

## 11. Gate 6: measured optimization, endurance, and Laputa delivery

### 11.1 Benchmark lanes

Keep collection, pure update/render, terminal transport, and startup costs separate. Otherwise a filesystem/cache change can be mistaken for a faster language runtime.

| Lane | Inputs | Measures |
|---|---|---|
| Parser/collector | Synthetic rooted trees and recorded scalar observations | Files/bytes read, parse time, allocations, source bounds |
| Pure update | Preloaded raw/typed samples with deterministic event stream | Identity join, deltas, sorting, tree construction, history updates |
| Pure render | Fixed model/config and viewport | Layout, surface construction, diff, encoded bytes, allocations |
| PTY end-to-end | Actual CLI, real terminal transport, scripted events | Input-to-present latency, cleanup, output backpressure |
| Live steady state | Pinned Linux environment, selected feature set | CPU time, RSS, sample delay/skew, descriptor count, terminal bytes |
| Startup | Cold and warm product invocation | Load/check/lower cost, time to first useful screen, retained frontend memory |

Use at least 10, 1,000, and 10,000 processes; process churn and stable sets; 1, 32, 128, and a large sparse CPU-ID case; small/normal/large terminal sizes; no-device and many-device inputs; and rapid resize/filter events. Synthetic scale cases must not require huge checked-in expanded trees: generate them reproducibly from a seed or share immutable fixture blobs.

At large process counts, preloaded update/render tests isolate language complexity from procfs overhead. Raw collection tests are still required; neither lane replaces the other.

Use the repository's release profiling tools, including `xsht runtime-stats --json REPORT SCRIPT`, `xsht trace --syscalls --trace-top-syscalls 10 SCRIPT`, and the existing `bench/stdlib-port` conventions. Pair runtime allocation accounting with host RSS. Do not compare debug XSH with release btop. Run paired benchmarks serially and record hardware, CPU limits, compiler, binary hashes, feature set, and sample counts. [X3]

### 11.2 Proposed performance acceptance budgets

These are **engineering targets, not measured results from this research**. During preparation, name a benchmark runner/profile and record its baseline. Keep that runner/profile stable for the campaign; do not claim the same absolute limits on arbitrary machines.

For a normal profile of 1,000 synthetic processes, 32 logical CPUs, a `120×40` viewport, and a 2-second sampling interval, target:

| Measure | Gate-6 target on the named runner |
|---|---|
| Input-to-completed-present latency | p95 ≤ 50 ms and p99 ≤ 150 ms during ordinary collection/rendering |
| Frequent-source sample/update work | p95 ≤ 20% of the configured sampling interval |
| Preloaded model-update plus render/diff | p95 ≤ 50 ms |
| Unchanged display with decorative clock frozen | No content update bytes after the first committed frame |
| Process history matching | Indexed O(P) construction/lookups, not nested scans |
| 1,000 → 2,000 preloaded-process scaling | No quadratic trend; investigate a repeatable >3× median increase |
| Bounded caches/histories | Count bounds asserted directly; no retention proportional to elapsed run length |
| Endurance memory | After warm-up, the second equal-length replay window adds no sustained RSS trend; investigate growth beyond max(8 MiB, 10% of steady RSS) |

Stress profiles may miss the normal-profile latency budget, but must remain bounded and cancellable, report collection lag/partial status, and never queue work indefinitely. Do not hide missed sample deadlines by silently omitting required data. An expensive optional detail can be stale while core monitoring continues.

The numerical limits may be corrected for a demonstrably wrong benchmark definition or runner mismatch, with explicit independent evidence. Do not loosen them merely because optimization is inconvenient. A genuine unresolved performance failure remains a failure in the release report, not a silently edited baseline.

Measure upstream btop CPU time, memory, startup, and terminal bytes under comparable settings. Treat convergence toward its efficiency as an optimization objective, not a promised identical cost across languages. Report ratios and absolute values, with uncertainty, rather than claiming “near native” from one favorable microbenchmark.

### 11.3 Optimization order

Start with unnecessary work: repeated full inventory, repeated decoding/formatting, redundant full-frame output, expensive details for every process, repeated username lookup, stale caches that never expire, and sorting before filtering when semantics permit the reverse.

Then fix algorithms: indexed identity joins, one parent/child adjacency build, stable sort keys computed once, bounded histories, per-row or per-panel invalidation, bulk concatenation, and efficient canonical source parsing. Use top-k selection only when it preserves the complete sorting/tree/filter contract.

Then profile representation/runtime costs: collection updates causing full copies, record/map lookup overhead, repeated boxed scalar allocation, string/byte concatenation, parsing loops, sorting/comparator dispatch, and retained temporary state. Optimize the smallest generic operation and verify unrelated workloads.

Only then consider a new reusable runtime/API capability. Do not shortcut to a native `collect_all_system_metrics`, `render_btop`, specialized btop bytecode, or a second execution engine. XSH already has one checked/lowered/verified indexed executable form; preserve that architecture. [X2]

### 11.4 Endurance and fault testing

Run deterministic replays long enough to fill every history and cycle thousands of process/device identities. Compare early and late steady-state live object counts, RSS, descriptors, and update latency. Test pause/resume, repeated theme/preset changes, nested menu lifecycles, repeated terminal reopen where supported, and rapid resizing.

Exercise controlled failures: reader error bursts, a deliberately slow source, pending input during collection, broken output, malformed source text, terminal disconnect, and cancellation during each lifecycle phase. A stale sensor must not stall the process table. A closed terminal must not leave an orphan sampler. Disable test workloads afterward and reap all owned children.

Use bounded fuzz campaigns for the incremental terminal decoder, source parsers, config parser, graph/layout dimensions, and reducer event ordering. Seed from real regressions and shrink failures. Put language/runtime soundness regressions into the existing XSH fuzz corpus rather than building an unrelated fuzzing platform.

### 11.5 Packaging and Laputa

Integrate the applet into the current core packaging/alias/inventory mechanism after the relevant gates pass. Keep existing `top` behavior intact unless a separately tested migration is made. Reference-harness commands must use absolute reference-binary paths so an installed XSH `btop` alias cannot accidentally call itself as the oracle.

Verify on the repository's supported pinned Linux build path, then in an existing disposable Laputa VM or test image if available. Run as an ordinary owned process, not as PID 1. Do not replace init, change the user's boot chain, or construct a new hypervisor stack merely to test the monitor.

An Asterinas/Laputa guest is a useful additional capability/degradation lane if already available. Do not assume that identifying as Linux-compatible guarantees every procfs/sysfs source. Missing sources should be explicit and the monitor should remain usable. Building the Asterinas/Firecracker integration itself is not a prerequisite for this monitor campaign.

### Gate-6 exit conditions

The candidate has a usable installed entrypoint, a qualified Linux feature report, all deterministic gates, recorded terminal and collector evidence, measured performance/endurance results, updated public API/docs, and a clean set of scoped commits. ## 12. Deterministic fixtures, replay, and independent oracles

This is the campaign's core development loop. Implement the minimal version in Gate 1, then extend it as features demand. Do not postpone replay until after live collection is hard to disentangle.

### 12.1 Three fixture levels, three different claims

| Level | Input | What it proves |
|---|---|---|
| Raw-source replay | Bounded raw procfs/sysfs observations plus recorded OS scalars and events | Production acquisition/parsing, identity, derivation, reducer, and rendering |
| Typed model replay | Independently constructed typed samples and events | Pure state/layout/widget behavior, fast numerical/stress tests |
| PTY transport replay | Actual program plus raw input chunks, size changes, signals, and output capture | Descriptor/session lifecycle, byte decoding, presentation and cleanup |

Typed model fixtures are useful, but not a substitute for raw-source tests. PTY screenshots are useful, but not a substitute for typed numerical assertions. Report which layer each result exercises.

### 12.2 Minimal bundle format

Begin with a versioned directory containing:

```text
bundle/
  manifest.json               Version, provenance, configuration, units, bounds
  events.jsonl                Explicitly ordered virtual-time events
  snapshots/0000/root/...     Complete synthetic source tree at sample 0
  snapshots/0001/root/...     Complete synthetic source tree at sample 1
  observations.jsonl          Non-file OS results and exceptional source results
  expected/model.jsonl        Independently established semantic expectations
  expected/screens.jsonl      Canonical cells/styles for selected checkpoints
```

As scale grows, immutable blobs and snapshot deltas may replace repeated full trees. Keep the first format simple. Migration must preserve exact snapshot meaning and stable replay; never mutate the currently sampled tree while pretending the observation was atomic.

`manifest.json` records schema version, fixture/capture origin, source session/boot/scope identity, page size, ticks/second, display policy, initial dimensions, configuration, content digests, and limits. Preserve original raw counters without float rounding. Do not confuse a synthetic fixture with a captured physical host.

Events have a sequence number, virtual timestamp, kind, and typed payload. Relevant kinds include sample request/completion, key/text input, raw input chunk, escape timeout, resize, selection-dependent effect result, configuration change, source/capability change, suspend/resume, and quit. Start with only the Gate-1 subset.

Define a total order, for example `(timestamp, sequence)`, and reject duplicates or invalid ordering under a documented rule. A synchronous minimal loop can expose completed sample events directly. When asynchronous acquisition is introduced, recorded completion order—not nominal request order—must determine observed transitions.

Freeze randomness by seed, wall clock by explicit decorative-clock input, monotonic time by event/source timestamps, environment/config by the manifest, and terminal policy by capabilities. Never consult the live system to fill a missing replay field.

### 12.3 Filesystem observations and non-file observations

Reuse `FsRoot` for normal raw-tree replay. Reuse `sys_source`'s complete-read rules and error vocabulary. Every input path must remain within the allowed rooted bundle; reject traversal, unsafe symlink escape, unexpected device files, and unbounded lists/data. Capturing a sysfs description never authorizes reading a raw block device.

A plain tree cannot reproduce every kernel interaction. Record page size, clock units, monotonic readings, mount-capacity results, and vendor/syscall results explicitly. A fixture root must never fall back to the live host for these.

Permission failures and races need extra care: `chmod 000` is not a reliable permission-denial fixture when the test runs as root, and two static snapshot directories do not simulate a process changing between two reads in one collection pass.

Use existing test mocks if they can intercept the rooted read boundary. Otherwise add the smallest reusable observation adapter/test seam that can return the same raw read/enumeration/result shapes, including per-operation ordering, errno, disappearance, and truncation. Keep all real parsers downstream unchanged. Do not build a general virtual filesystem framework, and do not inject already-derived CPU percentages to “test” a raw collector.

A recorded observation tape should detect unexpected extra reads, wrong paths, wrong read limits, or wrong read order when the fixture specifies them. Less order-sensitive fixtures can key by operation/path/ordinal and explicitly permit independent enumeration order. The policy must be part of the fixture, not an implicit global relaxation.

### 12.4 Preserve the report harness's useful evidence model

The existing report checker distinguishes synthetic fixtures, raw capture/replay, and live bracketed comparisons; validates raw bytes and metadata before and after replay; and keeps a fixed denominator. Reuse these ideas and small common utilities where they are genuinely shared. [X4, X7]

Keep live captures private, preferably mode `0700`, outside tracked source. Raw process names, arguments, host IDs, paths, device labels, and screenshots can disclose information. Hashing a file does not anonymize its contents. Never auto-commit a raw host capture. Synthetic fixtures are the default checked-in corpus.

Capture full arguments only under separate explicit authorization. Never capture process environments. Bound files, entries, nesting, total bytes, event count, and replay duration/work. A replay bundle is untrusted input.

### 12.5 Independent numerical oracle

For simple fixtures, write expected arithmetic directly from the fixture specification, such as the Gate-1 example. For richer captures, use a development-only independent decoder/calculator or a pinned reference utility. It must not import the candidate's parsing/rate helpers.

Check raw identity, units, availability, and derived values separately. An oracle disagreement may be a candidate bug, a reference bug, or a genuine convention difference. Resolve it from the pinned implementation and kernel ABI contract; do not average the values or expand tolerances until the result becomes green.

When live counters are monotonic, a bracketing reference may validate interval inclusion. A gauge needs a stable or explicitly bounded relationship. A live reference that changed or lacks permission remains unstable/unavailable, not an exact match. Preserve the report harness's distinction between eligibility and candidate success.

### 12.6 Upstream btop as a reference, without magical fixture support

Do not assume unmodified btop accepts a source-root, replay stream, or JSON telemetry option. Its platform collectors are live-system implementations. Two applications reading the same live machine at different times do not provide deterministic screen equivalence.

Use three complementary reference methods:

1. **Pinned source-derived tests** for formulas, graph quantization, config defaults, key behavior, and layout rules. Keep expected values independently calculated.
2. **Controlled live runs** with the same terminal/configuration and bracketed telemetry; limit exact assertions to stable comparable facts.
3. **A narrow development-only upstream adapter** when exact renderer/input parity is needed: inject shared collector structs and virtual time into the pinned reference, or redirect the smallest raw-source/clock boundary required by that test. Preserve the original draw/input algorithms. Record the patch digest and compare an unmodified live build on representative cases to ensure the adapter did not rewrite the oracle.

Do not make a complete upstream collector replay retrofit a prerequisite for Gate 1. Its raw numerical fixture and actual-PTY gate are sufficient for the thin slice. Add a focused graph/render adapter during the visual hillclimb, where it yields real leverage.

A manually recreated “btop reference” that uses the same XSH algorithm is not an independent oracle. Do not patch upstream until it agrees with the candidate.

### 12.7 Independent screen/transport oracle

The production renderer exposes a canonical semantic surface for native tests. Separately, a development-only terminal decoder consumes the actual ANSI output of the CLI/PTY run and reconstructs its screen state. Use existing test utilities or a small audited test dependency if adequate; do not build a full terminal emulator project.

The decoder must support every sequence the product emits, reject unsupported output instead of silently ignoring it, and not share the candidate's damage algorithm. Compare effective cells/styles and cursor state at declared frame checkpoints. Keep raw bytes as diagnostic artifacts, not the only golden format.

For every delta-render test, also render the destination as a fresh full frame and require the same decoded terminal state. Inject partial output boundaries and resize between frames. This catches stale tails, invalid damage assumptions, style leakage, and wide-character artifacts that direct surface tests cannot catch.

An optional HTML/text mismatch viewer is useful: show model differences, event index, expected/actual screen, differing cells and styles, and the minimal reproducer. It must not become an application dependency or a prerequisite for automated pass/fail.

### 12.8 Golden changes and harness self-tests

Never blindly replace a failing golden with current output. Require a stated expected-behavior change, an independent source or arithmetic explanation, and a focused test. The agent can correct a genuinely defective oracle unattended when independent evidence proves the defect, but must record the correction and preserve the prior failure/reason in the commit summary.

Test the checker itself: changed raw bytes, changed metadata, missing expected assertion, contradictory observed/error state, duplicate event IDs, unknown schema, incompatible units, wrong oracle digest, an unexercised hardware capability, and candidate-declared `unsupported` for a required fixture must all be detected correctly.

## 14. Coverage ledger and autonomous hillclimb

### 14.1 Assertion schema

Base the ledger on the report checker's useful fields, but keep this campaign independently navigable. A proposed assertion record is:

```json
{
  "id": "cpu.aggregate.interval",
  "gate": 1,
  "domain": "cpu",
  "upstream_commit": "6e39144aaf5a6bc01b9f795010b0914431067183",
  "upstream_source": "src/linux/btop_collect.cpp",
  "candidate_owner": "core/lib/btop_rates.xsh",
  "relation": "derived_metric",
  "source_abi": "linux.proc.stat",
  "eligibility": "fixture supplies two complete same-scope samples",
  "equality_rule": "exact rational derivation; declared display rounding",
  "fixture_scenarios": ["basic-two-sample", "cold-start", "idle-interval"],
  "native_tests": [],
  "pty_tests": [],
  "implementation_status": "pending",
  "verification_status": "not_run"
}
```

The empty test lists above are an illustrative preparation state, not an acceptable passed assertion. Require concrete existing test identifiers and actual evidence before a gate can pass. Keep implementation status independent from verification status.

Suggested result vocabulary: `passed`, `failed`, `not_run`, `reference_unavailable`, `hardware_unavailable`, `permission_limited`, `unstable`, and `not_applicable_by_pinned_contract`. An absent device in one run does not remove that device family's deterministic implementation requirements.

Group scores by gate, domain, platform, and evidence type. Show the fixed required count, eligible count, passed count, and each non-pass class. Avoid one attractive composite percentage that hides missing process actions or a completely untested GPU vendor.

### 14.2 Iteration algorithm

Use a small closed loop:

```text
choose the earliest unsatisfied gate
  -> choose its highest-impact failing or missing assertion
  -> reproduce with the smallest raw/event fixture
  -> establish expected behavior independently
  -> implement the XSH behavior
  -> add the smallest justified generic capability only if required
  -> run targeted native tests and the relevant host boundary
  -> compare semantic model, cells, and measurements
  -> minimize any regression
  -> update evidence and commit a coherent increment
  -> repeat without waiting for another user instruction
```

Rank work lexicographically: safety/correctness and architecture violations first; completion of the current gate next; then compatibility coverage; then measured latency, CPU, memory, and output improvements. Do not accept a faster wrong result, a higher visual score obtained by masking fields, or a larger feature count obtained by stubbing data.

Use the fixed upstream feature inventory to choose the next slice. Avoid spending a cycle on a theme while process identity is wrong, or adding unrelated Linux extensions while required input/config behavior remains missing.

### 14.3 Progress and commits

Keep `dev/btop-progress.json` small: current gate, last known-good commit, active assertion IDs, evidence locations, exact failing reproducer, measured baseline, next executable actions, and external blockers. Large logs, profiles, binary references, and real captures stay ignored; retain small synthetic fixtures and summarized evidence needed to reproduce results.

Preserve the user's unrelated working-tree changes. Do not reset or rewrite their work. Commit cohesive changes with tests and the corresponding contract updates. Push only under the repository/user's existing authorized workflow; this campaign is not permission to change remote permissions, branch protection, or external services.

At a genuine execution/context limit, leave a precise resumable checkpoint. Do not turn that into a false completion claim or a strategic pause after Gate 1. The next execution should be able to continue from the ledger without rediscovering the project.

### 14.4 What counts as completion

A qualified Linux completion requires all mandatory deterministic and terminal gates, implemented in-scope Linux features, preserved existing contracts, measured release behavior, usable packaging, and an explicit hardware verification table. A pending live hardware lane can be reported as unexercised; a missing implementation cannot be disguised as unavailable hardware.

If a required feature or performance gate remains unresolved, state that exactly and preserve its reproducer. Continue all runnable work. Do not write “full btop parity” without naming the pinned release, platform, intentional differences, and unexercised capabilities.

## 15. XSH language/runtime expansion protocol

Expansion is encouraged when it makes the language genuinely better. Each change should have a short implementation note answering:

```text
Need:              Which concrete application behavior is missing or inefficient?
Existing surface:  What existing APIs/idioms were inspected and tried?
Evidence:          Minimal reproducer and, for performance, measured profile.
Smallest change:   Why this belongs in a general API/runtime rather than btop code.
Contract:          Types, effects, ownership, cleanup, errors, bounds, determinism.
Independent use:   At least one non-btop test/workload that benefits or guards behavior.
Verification:      Native contract tests, host tests where needed, regression results.
Cost:              Dependencies, binary/build cost, allocations, platform requirements.
```

Good likely candidates include terminal ownership/polling, monotonic deadlines, cell-width/Unicode operations, bounded byte scanning, exact counter arithmetic, bulk buffer construction, efficient map/update primitives, and generic collection/runtime improvements. They are candidates, not a predetermined list of features to add without evidence.

Keep user-space monitoring semantics and UI algorithms in XSH. Native code should not know what a CPU panel, process sort mode, network graph scale, or selected btop row means. A generic surface transport operation must not gradually become a hidden native layout/widget engine.

Use the current compiler pipeline. Update parser/checker/lowering/verifier and registry facts coherently if a true language change is necessary; do not add an alternate interpreter or a fallback for constructs the main pipeline cannot execute. Prefer a library/API or representation improvement over new syntax when it expresses the behavior cleanly. [X2]

Where a generic operation is accelerated, retain an XSH-level reference implementation in tests when practical, verify equivalence under randomized inputs, and measure both the monitor and an unrelated workload. A microbenchmark improvement that worsens full source checking, allocations, or normal scripts is not automatically a win.

The initial product is a Linux monitor with portable pure logic. The first additional live platform should be macOS, aligning with existing XSH host support. Do not silently exclude those systems and call the result an all-platform port; do not spend the Linux campaign porting the entire XSH runtime to an unsupported OS ahead of its requested monitor.
