# Checked Int arithmetic in Millipede

This package tests a route from XSH's independent checked arithmetic definition to a Millipede x86-64 executable. It is an experiment and does not replace XSH's Rust implementation.

`Xsh.Core.Arith.checked` in `../../formal/Xsh/Core/Arith.lean` defines the expected result. The operands are representable signed 64-bit integers. Division and remainder truncate toward zero. Division by zero produces `divisionByZero`. `MIN / -1` and `MIN % -1` both produce `overflow`, because XSH checks the quotient for both operations.

`Arith.lean` defines the operations with `mp def`. The operands and result are two's-complement words. A result has tag 0 for success, 1 for overflow, and 2 for division by zero. Error results have a zero word. `Proof.lean` defines `expected` directly as `Xsh.Core.Arith.checked`. `encode` converts an integer to its 64-bit two's-complement word. `Canonical` permits all success words and only zero error words. The canonical restriction is necessary for an injective decoder. `checkedOp_canonical` proves that every `checkedOp` result has that form.

The principal statements, in the namespace `MillipedeArith`, are:

```lean
theorem decodeAnswer_injective : Function.Injective decodeAnswer

theorem checkedOp_canonical (op a b : UInt64) :
    Canonical (checkedOp op a b).run

theorem checked_answer_refines (op : IntOp) (a b : Int)
    (ha : Representable a) (hb : Representable b) :
    decodeAnswer ⟨(checkedOp (opCode op) (encode a) (encode b)).run,
      checkedOp_canonical (opCode op) (encode a) (encode b)⟩ = expected op a b

theorem checked_refines (op : IntOp) (a b : Int)
    (ha : Representable a) (hb : Representable b) :
    decode (view (checkedOp (opCode op) (encode a) (encode b)).run) = expected op a b

theorem core_refines (op : IntOp) (a b : Int)
    (ha : Representable a) (hb : Representable b)
    (ω : Millipede.Oracle) (w : Millipede.World) :
    decode (view ((Millipede.Exp.denote ω checkedOp.exp
      (Millipede.Env.cons (encode b) (Millipede.Env.cons (encode a)
        (Millipede.Env.cons (opCode op) Millipede.Env.nil))) w).1)) = expected op a b
```

`core_refines` uses the kernel-checked equation generated by `mp def`:

```lean
checkedOp.exp_denote (ω : Millipede.Oracle) (w : Millipede.World) (op a b : UInt64) :
  Millipede.Exp.denote ω checkedOp.exp
    (Millipede.Env.cons b (Millipede.Env.cons a (Millipede.Env.cons op Millipede.Env.nil))) w =
  ((checkedOp op a b).run, w)
```

The compiler theorem is `Millipede.compile_sound : Millipede.CompileSound.Statement Millipede.compile Millipede.x64Linux`. Its statement is:

```lean
∀ (p : Program) (b : ByteArray), compile p x64Linux = .ok b → p.Safe →
  ∃ s₀, x64Linux.fmt.load b.data.toList = some s₀ ∧
    ∀ ω : Oracle,
      let m := Machine.run x64Linux s₀ ω
      m.NeverStuck ∧ TraceEq m.trace (p.events ω) ∧
      m.StackWithin (p.stackBytes x64Linux.φ) ∧
      m.StepsWithin (p.events ω) (fun k => p.stepCost k ω x64Linux.κ)
```

`program.safe` discharges the safety premise. `#mp_compile program` ran the default compiler and reported the produced bytes, discharging the successful compilation premise by execution. The package does not contain a kernel proof of that compilation equation. The equation for `checkedOp.exp` applies to the Core function called by the reactor. The compiler theorem carries the reactor's source trace to the modeled machine trace. This package does not prove a source-trace specification for the framing protocol or connect every possible reactor trace to `checked_answer_refines`. The executable vectors exercise that connection on the listed inputs.

The theorem describes Millipede's x86-64 instruction, ELF loader, and Linux syscall models. The Lean kernel, Lean's compiler and runtime used to run the compiler, and the correspondence of those models to the machine and Linux are trusted. The loader model assumes the documented x64 Linux address layout, 4096-byte pages, and sufficient stack space under `RLIMIT_STACK`. The syscall model admits arbitrary oracle results and bytes. The reactor expects Linux `read`, `write`, and `exit`; a read error is treated like the end of input by the single-byte read binding. A truncated request exits with status 1. An unrecognized op byte uses remainder. The byte protocol's behavior under arbitrary syscall answers is not separately proved here. The generated `.lake/millipede-arith.ledger.txt` records the models and bounds in more detail.

Each request is 17 bytes: an op byte 0 through 4 for add, sub, mul, div, or rem, then two little-endian 64-bit words. Each response is a tag byte and a little-endian 64-bit word. The reactor accumulates one input byte per step and emits one response byte per step. It retries a zero-length write. It exits when input ends at a request boundary.

From this directory, run:

```sh
export TMPDIR="$PWD/../../.work/tmp"
mkdir -p "$TMPDIR"
lake build
printf '%s\n' 'import Proof' \
  '#print axioms MillipedeArith.checked_answer_refines' \
  '#print axioms MillipedeArith.core_refines' \
  '#print axioms MillipedeArith.decodeAnswer_injective' | lake env lean --stdin
./vectors.sh
./profile.py
```

`vectors.sh` evaluates `Xsh.Core.Arith.checked` in Lean to create the expected bytes, runs the generated ELF, and compares all response bytes. It tests 16 fixed operand pairs for each operation and 128 deterministic pseudorandom pairs for each operation, for 720 requests. The fixed cases include zero, one, the extrema, minus one, both zero-divisor operations, both MIN and minus-one operations, signed add, sub, and mul overflow in both directions, and mixed signs for division and remainder. The script exits nonzero on generation, execution, or comparison failure.

On this host, after `lake clean millipede_arith` with dependencies already built, `/usr/bin/time lake build` took 11.74 seconds wall time and 2,002,924 KiB maximum resident memory. This is a warm dependency build, not the time to fetch and build Millipede from scratch. `#mp_report` reported a 12,288-byte x64 ELF, 7,800 bytes of stack, at most 288 instructions for init, and at most 3,016 instructions for each step under its x64 cost model. The ledger explains the per-oracle interpretation of the step bound. These figures are not a speed comparison.

`profile.py` runs Lean's declaration profiler over the proofs and reports elapsed elaboration for each theorem, including tactic work and checking. The run used 6.29 seconds wall time.
