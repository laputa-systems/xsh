# Operand-order review for the e048b33 route matrix

This review covers the 87 `runtime_operand_order` gaps that had no source-order candidate in the 2026-10-16 final route matrix. It records source traversal and assertion evidence, then adds focused native assertions where source syntax has competing effectful operands. It does not change language/runtime behavior.

## Finding

The source supports written-order evaluation for named arguments that later occupy a different parameter slot. `lower_call` routes ordinary named entries through `lower_named_spread_call` (`src/runtime/eval/lower/calls.rs:463-475`). `lower_expanded_argument_values` lowers entries in authored order and stores each in a slot (`src/runtime/eval/lower/arguments.rs:214-320`); `wrap_argument_bindings` nests those assignments in execution order (`:322-335`). The resulting instruction row can therefore list parameter slots in a different order without reordering effects. `lower_function_call_args` also documents this distinction (`src/runtime/eval/lower/arguments.rs:450-451`).

The interpreter has two relevant traversal paths. The normal in-place evaluator walks comparison links and selects expression branches in source order (`src/runtime/eval/lowered_run/indexed_run.rs:1358-1459`). The explicit runner uses typed continuations: expression selection and calls start in `eval_expr_view` (`src/runtime/eval/lowered_run/indexed_run/explicit_run.rs:6499-7354`); generic module arguments advance their argument cursor in `step_module_arguments` (`:10531-10587`); process run operands proceed through target, args, environment, redirections, then options in `step_process_run` (`:3854-4055`); statement tags dispatch in `eval_statement` (`:5581-6257`). Frame-apply rows use `indexed_frame_apply_child` to choose actual operands and `ApplyOperands` to advance one child at a time (`src/runtime/eval/lowered_run/indexed_run.rs:452-674`, `src/runtime/eval/lowered_run/indexed_run/explicit_run.rs:8418-8480`). Those static child lists describe the post-lowering row. For calls with source-order bindings, they are not evidence that named argument effects ran in that list order.

## Rows with one source child or no source operand

These rows have no source child or one scalar evaluator child. Nested effects belong to the child expression's own row. `ExprIndexFromEnd` has a literal distance rather than a second expression, and `ExprStrByteLen` has only its receiver.

`BoolNot`; `ExprPathFrom`, `ExprField`, `ExprIndexFromEnd`, `ExprStrByteLen`, `ExprRequire`, `ExprCheckedValue`, `ExprSpawnCommand`, `ExprWait`, `ExprAbort`, `ExprFail`, `ExprOk`, `ExprTry`, `ExprProcCallResult`; `ExprPathReadText`, `ExprPathReadBytes`, `ExprPathExists`, `ExprPathExecutable`, `ExprPathDu`, `ExprPathMetadata`, `ExprPathReadlink`, `ExprPathResolve`; `StmtLet`, `StmtLetInt`, `StmtLetBool`, `StmtAssign`, `StmtAssignField`, `StmtAssignFieldInt`, `StmtAssignInt`, `StmtAssignBool`, `StmtValue`, `StmtExpr`, `StmtLetRecord`, `StmtRun`, `StmtReturn`, `StmtYield`, `StmtYieldDelegate`, `StmtBreakValue`, `StmtDefer`, `StmtDefaultParameter`.

`ExprFsMkdir` and `ExprFsRemove` are compiler-generated for `tempdir` scopes. The scope supplies the path expression, while `mkdir` has no optional expression and `remove` has a literal `missing_ok: true`; no source form gives these rows two effectful operands. `ExprProcessCommandArgv` is another special case: source-named arguments have already been evaluated by the binding wrapper before frame-apply consumes the assembled command. Do not infer their source effect order from the typed view's static field list.

`IntStrByteAtSlot` can contain an index and default, but both are pure `Int` subtrees. `tests/xsh/operand-order-scalars.xsh::test_operand_order_int_byte_at_uses_index_and_static_default` checks the index overflow path and the fixed fallback value; there is no effectful sibling-order candidate.

## Remaining order-coverage gaps and smallest evidence contract

Four independent order gaps now have assertions in `tests/xsh/operand-order-resume-oracles.xsh`: `test_path_mkdir_and_remove_evaluate_paths_before_optional_values`, `test_module_method_named_arguments_keep_written_order`, `test_pipeline_callbacks_run_across_stage_boundaries_in_order`, and `test_self_call_runs_multiple_named_arguments_in_written_order`. All four passed exact normal and forced-frame runs against the qualified e048 products; these historical runs do not replace the final-freeze route receipts. `ExprFsMkdir`/`ExprFsRemove` have no user source case with competing effectful operands, and `json.encode` cannot name its required `value` argument; the module-call oracle uses public `FsRoot.symlink(path:, target:)` syntax opposite to the API parameter order.

`ExprSpawnRun` and `ExprProcessCommandBuilder` remain pending a contract decision. SPEC §1 says evaluation order is source order, and §11.3 writes options and environment assignments before the target; the reviewed handlers traverse target, arguments, environment, redirections, then options. The existing process-frame oracle checks the evaluator's target-before-environment phase order. Draft probes named `test_spawn_run_operands_keep_target_arguments_overlay_and_option_order` and `test_process_command_builder_runs_environment_and_options_after_target` passed against e048 in normal and forced-frame modes, but they assert current phase order and do not prove the SPEC's source-order contract. Keep them out of candidate receipts until the user decides whether process syntax has a documented phase-order exception or must follow source order.

For a source-order candidate, require all three of: a source occurrence of the exact constructor/call form, at least two effectful operands whose authored order is observable (or a failure proving a later operand did not run), and a native assertion for that order. A one-child row is not an order candidate. For named calls, use authored argument-entry order plus the binding wrapper as the source proof; parameter-slot order, schema-field order, and the runtime row's post-binding projections are insufficient. Keep static traversal findings separate from exact normal/forced execution receipts.
