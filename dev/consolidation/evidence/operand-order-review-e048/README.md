# Operand-order review for the e048b33 route matrix

This review covers the 87 `runtime_operand_order` gaps with no source-order candidate in the 2026-10-16 final route matrix. It reads source and existing native assertions only. It does not claim current normal/forced execution receipts or add a language/runtime change.

## Finding

The source supports written-order evaluation for named arguments that later occupy a different parameter slot. `lower_call` routes ordinary named entries through `lower_named_spread_call` (`src/runtime/eval/lower/calls.rs:463-475`). `lower_expanded_argument_values` lowers entries in authored order and stores each in a slot (`src/runtime/eval/lower/arguments.rs:214-320`); `wrap_argument_bindings` nests those assignments in execution order (`:322-335`). The resulting instruction row can therefore list parameter slots in a different order without reordering effects. `lower_function_call_args` also documents this distinction (`src/runtime/eval/lower/arguments.rs:450-451`).

The interpreter has two relevant traversal paths. The normal in-place evaluator walks comparison links and selects expression branches in source order (`src/runtime/eval/lowered_run/indexed_run.rs:1358-1459`). The explicit runner uses typed continuations: expression selection and calls start in `eval_expr_view` (`src/runtime/eval/lowered_run/indexed_run/explicit_run.rs:6499-7354`); generic module arguments advance their argument cursor in `step_module_arguments` (`:10531-10587`); process run operands proceed through target, args, environment, redirections, then options in `step_process_run` (`:3854-4055`); statement tags dispatch in `eval_statement` (`:5581-6257`). Frame-apply rows use `indexed_frame_apply_child` to choose actual operands and `ApplyOperands` to advance one child at a time (`src/runtime/eval/lowered_run/indexed_run.rs:452-674`, `src/runtime/eval/lowered_run/indexed_run/explicit_run.rs:8418-8480`). Those static child lists describe the post-lowering row. For calls with source-order bindings, they are not evidence that named argument effects ran in that list order.

## Rows with no sibling effect order

These tags either have no evaluable child or only one direct expression child. They should not need a sibling-order candidate; any nested block or call has its own row and order evidence.

`ExprSpawnCommand`, `ExprWait`, `ExprCapture`, `ExprValueBlock`, `ExprLoop`, `ExprAbort`, `ExprFail`, `ExprOk`, `ExprTry`, `ExprProcCallResult`; `ExprPathReadText`, `ExprPathReadBytes`, `ExprPathExists`, `ExprPathExecutable`, `ExprPathDu`, `ExprPathMetadata`, `ExprPathReadlink`, `ExprPathResolve`; `StmtLet`, `StmtLetInt`, `StmtLetBool`, `StmtAssign`, `StmtAssignField`, `StmtAssignFieldInt`, `StmtAssignInt`, `StmtAssignBool`, `StmtValue`, `StmtExpr`, `StmtLetRecord`, `StmtReturn`, `StmtYield`, `StmtYieldDelegate`, `StmtBreakValue`, `StmtDefer`, `StmtDefaultParameter`.

`ExprProcessCommandArgv` is a special case: its typed view has several fields, but source-named arguments have already been evaluated by the binding wrapper before frame-apply consumes the assembled command. Do not infer their source effect order from the typed view's static field list.

## Remaining order-coverage gaps and smallest evidence contract

No behavior defect was established. Static order and existing assertions support the source-order behavior above; no native or normal/forced tests were run in this review. The most concrete missing side-effect assertions are: (1) `ExprSpawnRun` with marked target/args/env operands; (2) `ExprProcessCommandBuilder` with marked run environment and later options; (3) `ExprFsMkdir`/`ExprFsRemove` root operations with marked receiver, path, and optional boolean; (4) path mkdir/remove with an effectful optional value; (5) generic `ExprModuleCall` with named arguments authored opposite their parameter order; and (6) multi-stage `ExprPipeline` callbacks with visible effects across stage boundaries. Existing generic-module coverage uses canonical `json.encode(value, pretty:)` order. The path-operation route tests currently mark the receiver but use literal optional values.

For a source-order candidate, require all three of: a source occurrence of the exact constructor/call form, at least two effectful operands whose authored order is observable (or a failure proving a later operand did not run), and a native assertion for that order. A one-child row is not an order candidate. For named calls, use authored argument-entry order plus the binding wrapper as the source proof; parameter-slot order, schema-field order, and the runtime row's post-binding projections are insufficient. Keep static traversal findings separate from exact normal/forced execution receipts.
